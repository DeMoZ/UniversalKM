# Design

## Context

Зачем — proposal.md. До изменения `AndroidHIDTransport.startADB` запускал `adb start-server` через `Process`, а при пропаже сервера `adb track-devices` запускался снова и сам поднимал новый сервер. Сервер — процесс `adb -L tcp:5037 fork-server server`. После старта его родитель — `launchd`, но ответственным процессом macOS запоминает того, кто его запустил (UniversalKM). Доступ к локальной сети macOS проверяет по разрешению ответственного процесса, и только пока тот работает.

Проверки 2026‑11‑09 (macOS 27.0.1, S10e и SM‑X115 по Wi‑Fi):

| Кто запустил сервер | Пока запустивший работает | После его выхода |
|---|---|---|
| UniversalKM (обычный `Process`) | работает | «No route to host» (журнал `adb`, 14:15:28 и 14:46:09) |
| Оболочка в терминале | работает | — (терминал не закрывали) |
| Отказ от ответственности, до разрешения | «No route to host», запрос macOS для `adb` | — |
| Отказ от ответственности, после разрешения | работает | работает (pid 98418, 914, 1763) |

Ещё: сломанный сервер от прошлого запуска UniversalKM снова работает, как только UniversalKM запущен опять (pid 1205). Поэтому самому приложению ломалось не всегда, а `adb` в Терминале после выхода ломался всегда.

## Goals / Non-Goals

**Goals:** сервер, запущенный приложением, не зависит от того, работает ли приложение.

**Non-Goals:** не встраиваем свой `adb` и не меняем порт 5037 (общий сервер с Android Studio и Терминалом — решение транспорта D5). Не чиним серверы, которые запустили другие программы.

## Decisions

### D1. Сервер запускается с отказом от ответственности
`ADBClient.ensureServer` выполняет `adb start-server` через `DisclaimedSpawn.run`: это `posix_spawn` с `responsibility_spawnattrs_setdisclaim(attr, 1)`, функция ищется через `dlsym`. Клиент `adb` отвечает сам за себя, сервер, который он порождает, — тоже, и разрешение «Локальная сеть» у него своё. `ensureServer` вызывается при старте и перед каждым повторным запуском `track-devices`: иначе новый сервер поднял бы `track-devices`, запущенный обычным `Process`, и он снова считался бы частью приложения. Остальные команды `adb` (`shell`, `connect`, `push`…) — клиенты; с сервером они говорят через `localhost`, а это не локальная сеть.
*Альтернативы:*
- Останавливать свой сервер при выходе. Обрывает чужие сессии (`logcat` по USB, Android Studio), а сервер, поднятый Терминалом, всё равно требует, чтобы терминал работал. Сделано было сначала, заменено этим решением.
- LaunchAgent для сервера. Процесс от `launchd` тоже отвечает сам за себя, то есть тот же запрос для `adb`, только сложнее.
- Перезапуск сломанного сервера (TCP‑проверка адреса из приложения при «No route to host»). Не понадобился: работающий UniversalKM сам возвращает сломанному серверу сеть, а новые серверы больше не ломаются. Убрано, чтобы не держать непроверенный код.

## Risks / Trade-offs

- [`responsibility_spawnattrs_setdisclaim` — закрытый вызов, его могут убрать] → `dlsym`: без него сервер запускается как раньше, с прежней ошибкой, но ничего не падает.
- [Пользователь отказал `adb` в запросе «Локальная сеть»] → Wi‑Fi не работает и в приложении. README: «Системные настройки → Конфиденциальность и безопасность → Локальная сеть → adb».
- [Обновление platform-tools меняет путь к `adb` (`Caskroom/<версия>`)] → Запрос появится ещё раз. В README.
- [Сервер уже запущен кем‑то обычным способом] → `start-server` его не трогает; поведение как раньше.
