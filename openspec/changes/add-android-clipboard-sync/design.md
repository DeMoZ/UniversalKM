# Design

## Context

Зачем — proposal.md, раздел «Why». Требования — `specs/android-clipboard-sync/spec.md`. Изменение строится поверх `add-android-usb-transport` (ссылки «транспорт D1…D7» — на его design.md).

Что есть сейчас (по коду):

- `AndroidHIDTransport` знает, какие транспорты `adb` есть у каждого Android‑peer ID (`candidates(_:)`: USB‑серийный или `ip:port`/mDNS) и следит за ними через `ADBClient.track`. Ввод идёт через `ADBLink` (`adb -s <transport> shell hid -`, JSON по stdin) или через AOA. AOA HID не переводит телефон в режим accessory, поэтому при включённой отладке по USB рядом с AOA остаётся USB‑транспорт `adb` (таблица режимов в транспорт design, Context).
- `ADBClient` находит `adb` пользователя и запускает команды. `ADBLink` уже умеет держать долгий процесс `adb shell`, замечать его выход и проверять связь (heartbeat по сети).
- На Mac есть Android SDK пользователя (`~/Library/Android/sdk`: build‑tools 34/35 с `d8`, platform android‑34) и `javac` 25. Это нужно только для пересборки помощника, не для сборки приложения.

Ограничения Android: с Android 10 фоновое приложение не может читать буфер обмена. Процесс, запущенный через `app_process` от пользователя `shell`, обращается к системному сервису `clipboard` (`IClipboard`) от имени пакета `com.android.shell` и может читать, записывать и подписываться на изменения. Так работает scrcpy. Сигнатуры `getPrimaryClip` / `setPrimaryClip` / `addPrimaryClipChangedListener` менялись (добавлялись `attributionTag`, `userId`, `deviceId`).

## Goals / Non-Goals

**Goals:**
- Один долгоживущий помощник на телефон, без файлов вне `/data/local/tmp` и без процессов после отключения.
- Сборка приложения без Android SDK.
- Задержка ≤ 1 с в обе стороны, текст без искажений (UTF‑8).

**Non-Goals:**
- Не трогаем ввод: `ADBLink` и AOA не меняются, помощник буфера — отдельный процесс.
- Не делаем общий фреймворк «сервисов на телефоне». Протокол помощника — только буфер (версия в приветствии оставляет место на будущее).

## Decisions

### D1. Помощник: Java + `app_process`, не APK
Код на Java, собранный в `classes.dex` внутри `ukm-clipboard.jar`. Приложение кладёт файл через `adb push` в `/data/local/tmp/ukm-clipboard-<sha8>.jar` (хэш содержимого в имени, поэтому новая версия не путается со старой, а повторный push не нужен; перед push — проверка `ls`). Запуск: `adb -s <t> shell CLASSPATH=<path> app_process / com.universalkm.clipboard.Main`.
*Альтернативы:* APK с сервисом (нужна установка, фоновое чтение буфера всё равно запрещено). `cmd clipboard` (нет на многих версиях и нет подписки на изменения). Опрос `getPrimaryClip` по таймеру (лишняя нагрузка; оставлен как запасной путь, если подписка недоступна, — D3).

### D2. Протокол: строки JSON с base64 по stdin/stdout
Одна строка — один объект, `\n` в конце. Текст — base64 от UTF‑8, поэтому переводы строк и любые символы не ломают кадрирование.
- Mac → телефон: `{"t":"set","id":N,"b64":"…"}`, `{"t":"ping"}`.
- Телефон → Mac: `{"t":"hello","v":1,"sdk":31}` при старте, `{"t":"changed","b64":"…"}`, `{"t":"ack","id":N}`, `{"t":"pong"}`, `{"t":"error","msg":"…"}`.
Кодирование и разбор — в `UniversalKMCore/ClipboardProtocol.swift` (тестируется без устройства). Предел — 1 МБ текста до base64. Длиннее не отправляется ни одной стороной, и помощник проверяет то же самое.
*Альтернатива:* `adb forward` + сокет (лишний порт, сложнее жизненный цикл). stdin/stdout `adb shell` (shell v2, без pty) уже надёжно работает в `ADBLink`.

### D3. Помощник внутри
`Main` получает `IClipboard` через `ServiceManager.getService("clipboard")` и `IClipboard.Stub.asInterface` (reflection). Методы ищутся по имени, сигнатура перебирается от новой к старой, как в scrcpy. Подписка — `addPrimaryClipChangedListener` с `IOnPrimaryClipChangedListener.Stub`. Для этого нужен Looper: `Looper.prepareMainLooper()`, чтение stdin в отдельном потоке. Если подписаться не удалось, помощник опрашивает буфер раз в 500 мс и сравнивает текст. При `changed` берётся `coerceToText` первого элемента. После своей записи (`set`) помощник запоминает текст и не шлёт `changed` с тем же текстом (эхо гасится на обеих сторонах, D5). Закрытие stdin → `System.exit(0)`. Так помощник завершается и при выходе приложения, и при обрыве `adb`.

**Проверено 2026‑11‑09 (задачи 1.1–1.3).** S10e (Android 12, sdk 31) и Samsung SM‑X115 (Android 16, sdk 36): правило «самая длинная перегрузка, параметры по типу» подходит для `getPrimaryClip`, `setPrimaryClip` и `addPrimaryClipChangedListener` на обеих версиях. Подписка через `Proxy` + свой `Binder` работает (`watch: listener`), опрос не понадобился. На S10e текст доходит в обе стороны без искажений (кириллица, эмодзи, переводы строк, кавычки), включая копирование пальцем и переход помощника с Wi‑Fi на USB‑`adb`. После закрытия stdin процесса на телефоне нет. **Блокировка экрана:** пока телефон заблокирован, Android отдаёт пустой буфер (`getPrimaryClip` → null), поэтому изменения на телефоне не видны. Запись при этом работает: текст с Mac, отправленный во время блокировки, после разблокировки оказался в буфере телефона. Отдельная логика не нужна, на заблокированном телефоне всё равно нечего копировать.

### D4. Где помощник живёт в приложении
`ClipboardHelperLink` (по образцу `ADBLink`) — один процесс на телефон: push при необходимости, запуск, чтение строк stdout, запись stdin, `onLost`. Транспорт `adb` для него выбирается тем же правилом, что в транспорт D1, только без AOA: USB‑`adb`, если есть, иначе Wi‑Fi. При смене транспорта помощник перезапускается. `AndroidHIDTransport` публикует для каждого peer ID текущий `adb`‑транспорт (новое поле в `AndroidDeviceStatus`). `ClipboardSync` по этому полю, привязке к схеме и переключателю запускает и останавливает помощники. Heartbeat: `ping` раз в 2 с, без `pong` 5 с → потеря. Отдельный `cat`, как у `ADBLink`, не нужен.

### D5. Наблюдение за буфером Mac и защита от эха
`NSPasteboard.general.changeCount` проверяется раз в 300 мс (у macOS нет уведомления об изменении буфера). При новом `changeCount`: если среди типов есть `org.nspasteboard.ConcealedType`, `TransientType` или `AutoGeneratedType`, запись пропускается. Иначе берётся `string(forType: .string)`, и если текст отличается от последнего отправленного, он рассылается помощникам.
Защита от эха: `ClipboardSync` хранит последний текст, который сам записал в буфер Mac, и `changeCount` после записи. Изменение с этим `changeCount` не рассылается. Входящий `changed`, равный последнему тексту, отправленному на этот телефон, игнорируется. Текст с телефона кладётся в буфер Mac и запоминается как отправленный для всех телефонов. Поэтому он не уходит на другие телефоны: в спеке это требование «Два телефона». Если пользователь хочет переслать текст на второй телефон, он копирует его на Mac заново.
Текст буфера нигде не логируется: в журнале только длина и peer ID.

### D6. Запрос macOS на чтение буфера
Новые версии macOS могут показывать пользователю запрос, когда программа читает буфер без вставки (`NSPasteboard.accessBehavior`, `detect…`‑методы). Перед чтением проверяется `accessBehavior`. Если чтение запрещено (`.alwaysDeny`), панель показывает, что Mac → Android выключено системой, и где это разрешить; Android → Mac продолжает работать (запись разрешения не требует). Тип изменения сначала проверяется через `detect`‑методы, без чтения содержимого, так что картинки и скрытые данные не читаются вовсе. Проверено 2026‑11‑09 на macOS 27.0.1: у подписанного `UniversalKM.app` `accessBehavior` = 2 (`alwaysAllow`), запроса при фоновом чтении нет.

### D7. Сборка помощника
Исходник — `android/clipboard-helper/src/com/universalkm/clipboard/*.java`. Скрытые API — через reflection, поэтому компиляция идёт против обычного `android.jar`. `scripts/build-android-helper.sh`: `javac --release 11 -cp $ANDROID_HOME/platforms/android-34/android.jar` → `d8 --min-api 29` → `Resources/ukm-clipboard.jar`. Готовый jar хранится в репозитории (единицы КБ). `build-app.sh` только копирует его в `Contents/Resources`. Unit‑тест сверяет версию протокола: число `v` в Java и в `ClipboardProtocol` одинаковое (тест читает исходник Java как текст).
*Альтернатива:* собирать при каждой сборке приложения — тогда всем сборщикам нужен Android SDK.

## Risks / Trade-offs

- [Samsung или новая версия Android меняет `IClipboard`, и запись или подписка ломаются] → Перебор сигнатур (D3), запасной опрос, `error` с текстом в панели. Спайк 1.1 на S10e (Android 12) до основной работы.
- [Android 13+ показывает на телефоне всплывающее «скопировано в буфер» при каждой записи с Mac] → Это системное поведение, его не отключить. Записываем только при реальном изменении текста. Упоминается в README. На S10e (Android 12) окон‑тостов нет ни при чтении, ни при записи (проверено по `dumpsys window`). На SM‑X115 (Android 16) окно «скопировано» появляется при каждой записи с Mac, а сам буфер по Wi‑Fi работает в обе стороны (проверил пользователь 2026‑11‑09).
- [Опрос `NSPasteboard` раз в 300 мс] → `changeCount` дешёвый. Содержимое читается только при его изменении.
- [Секреты без пометки (пароль, скопированный вручную) уходят на телефон] → Переключатель у каждого телефона. В README сказано, что синхронизируется любой текст без пометки скрытого.
- [`adb push` при каждом запуске] → Имя с хэшем, push только если файла нет. Старые `ukm-clipboard-*.jar` удаляются после успешного запуска нового.
- [Связь `adb` по USB есть, но телефон показывает «Разрешить отладку?»] → Транспорт в состоянии `unauthorized` не используется. Панель показывает «недоступен» до разрешения.

## Migration Plan

Новых сохранённых данных, кроме флага у peer ID, нет. Флаг отсутствует → включён. Откат — удалить флаг и код. На телефоне остаётся только файл в `/data/local/tmp`, его удаляет следующий запуск или перезагрузка телефона (Samsung чистит `/data/local/tmp` не всегда, это не мешает).

## Open Questions

- Окно «скопировано» на Android 13+ подтверждено (Android 16). Убрать его нельзя: `ClipDescription.EXTRA_IS_SENSITIVE` только прячет текст в окне, и тогда на телефоне не видно, что пришло. Оставляем как есть; если будет мешать — отдельное изменение.
