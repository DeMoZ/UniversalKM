# Design

## Context

UniversalKM управляет iPhone через ChameleonUltra по Bluetooth: Chameleon для iPhone — клавиатура и мышь, данных по этому каналу нет. В приложении уже есть окно файлов Android (`FileBrowserView`, `FileBrowserTable`, `FileBrowserModel`): перетаскивание через `NSFilePromiseProvider`, ⌘C через временную папку, очередь переносов с отменой, клавиши при любой раскладке (`LatinKey`). У проекта самоподписанный сертификат без Apple Team ID, приложение не в песочнице.

Пользователю нужно главное: скопировать фото и видео с iPhone и удалить их с него.

## Goals / Non-Goals

**Goals:**
- Окно фото и видео iPhone или iPad на кабеле: миниатюры, копирование на Mac тремя способами, удаление с подтверждением.
- Понятные состояния: нет кабеля, заблокирован, нет доверия, удаление недоступно.
- Повторно использовать то, что уже сделано для Android: перенос, ⌘C, клавиши.

**Non-Goals:**
- Отправка фото на iPhone (через PTP нельзя, в медиатеку можно положить только через «Фото»).
- Файлы приложений и «Файлы» (AFC, house_arrest) — отдельное изменение, если понадобится.
- Работа по Wi‑Fi.
- Перевод HEIC в JPEG при копировании.

## Decisions

### D1. ImageCaptureCore, а не AFC

`ICDeviceBrowser` находит iPhone на кабеле как `ICCameraDevice`. `mediaFiles` даёт снимки, `requestThumbnail` — миниатюры, `requestDownloadFile` — файл, `requestDeleteFiles` — удаление из медиатеки. Это открытый API «Захвата изображений»: ему не нужны записи о доверии из `/var/db/lockdown`, TLS lockdown и Team ID.

Отвергнуто: AFC через `usbmuxd` (как libimobiledevice). Плюсы: работает по Wi‑Fi‑синхронизации, видит папки приложений. Минусы: шифрованный протокол со своей реализацией, а удаление файла из DCIM не убирает его из медиатеки, так что в «Фото» остаётся битая запись. Главная задача пользователя — удалять, поэтому AFC не подходит.

Ограничение: только кабель. Об этом сказано в окне и README.

### D2. Какое устройство показывать

Chameleon не знает UDID iPhone, поэтому окно не привязано к устройству в панели. Кнопка «Фото iPhone…» видна в панели, пока Apple-устройство на кабеле: `AppleDevicesOnCable` держит свой `ICDeviceBrowser` всё время работы приложения, но сессию не открывает и iPhone не занимает. Сначала кнопка была у выбранного не‑Android устройства, но тогда без iPhone на схеме её не найти (проверка пользователя). Окно показывает Apple-устройства с `ICCameraDevice` на кабеле: если одно — его, если несколько — выбор по имени (`ICDevice.name`). Одно окно на всё приложение, выбор запоминается в окне на время работы.

### D3. Сессия и состояния

Окно держит `ICDeviceBrowser` (`browsedDeviceTypeMask = .camera | .local`) только пока открыто, при закрытии закрывает сессию (`requestCloseSession`), чтобы не мешать «Фото» и «Захвату изображений».

Состояния:
- нет устройства → «Подключите iPhone кабелем»;
- `isAccessRestrictedAppleDevice` → «Разблокируйте iPhone и нажмите „Доверять“»;
- `isLocked` → «Разблокируйте iPhone»;
- сессия открыта, `deviceDidBecomeReady` → список.

Обрыв (`didRemoveDevice`) прерывает переносы с ошибкой «Связь с iPhone потеряна».

Есть ли разрешение macOS (TCC) на доступ к камерам-устройствам для не‑песочного приложения и какое у него окно, проверяет задача 1.1. `requestContentsAuthorization` на macOS недоступен, поэтому ожидаем, что разрешения нет.

### D4. Список: сетка миниатюр

`NSCollectionView` в `NSViewRepresentable` (сетка, выделение с ⌘/⇧, ⌘A, перетаскивание). `mediaFiles` плоский, папки DCIM пользователю не нужны. Сортировка по `creationDate` (новые сверху), подпись: имя, дата, размер, у видео — `duration`.

Миниатюры запрашиваются только для видимых ячеек, кэшируются в `NSCache`. Пока `deviceDidBecomeReady(withCompleteContentCatalog:)` не пришёл, видно «Прочитано N снимков».

iPhone составляет каталог в момент подключения кабеля (задача 1.1): снятое потом не приходит ни через `didAdd`, ни после перезапуска `ptpcamerad`, «Захват изображений» его тоже не видит. Окно под списком пишет «Новые снимки появятся после переподключения кабеля». `didAdd`/`didRemove` всё равно обрабатываются: они приходят при удалении и при подключении.

### D5. Копирование

`requestDownloadFile(_:options:…)` с `ICDownloadsDirectoryURL` = временная папка рядом с целевой (`.ukm-part-<uuid>/`), `ICSaveAsFilename` = исходное имя. После успеха файл переносится под свободное имя (`FileNames.unique`), при ошибке или отмене временная папка удаляется (`cancelDownload`).

- Перетаскивание — `NSFilePromiseProvider`, как в окне Android.
- ⌘C — скачать в `temporaryRoot/Copied/<uuid>/` и положить URL в буфер, как D8a окна Android.
- «Скачать…» — `NSOpenPanel` с выбором папки.

Live Photo (задача 1.1): в `mediaFiles` только HEIC, его видео — в `sidecarFiles` (IMG_xxxx.MOV), отдельной записи в каталоге нет. Опция `ICDownloadSidecarFiles` скачивает оба файла рядом. Окно помечает такую ячейку значком Live Photo, свободное имя на Mac выбирается для пары целиком, чтобы HEIC и MOV остались с одним базовым именем («IMG_0001 2.HEIC» и «IMG_0001 2.MOV»).

Очередь переносов: по одному файлу за раз (PTP-сессия одна), строки с ходом и «Отменить» — тот же вид, что `TransferRow` у Android. `TransferRow` и `FileTransfer` выносятся в общий файл, без изменения поведения окна Android.

### D6. Удаление

`requestDeleteFiles(_:deleteFailed:completion:)` с подтверждением `NSAlert` («Удалить N снимков с iPhone?», кнопка «Удалить» красная). Доступно, только если у устройства есть `ICCameraDeviceCanDeleteOneFile` и `isLocked == false`. Иначе кнопка недоступна, подсказка объясняет причину.

Проверено в задаче 1.1: обычное фото удаляется (`ICDeleteSuccessful`, `didRemove` сразу, на iPhone его нет). Live Photo, удалённое одним HEIC, iPhone тоже отвечает «удалено», но оставляет в «Фото», и после переподключения оно снова в каталоге. Удалённое вместе с видео из `sidecarFiles` пропадает и на iPhone. Поэтому окно всегда удаляет снимок вместе с его `sidecarFiles`. С включёнными «Фото iCloud» не проверено: у пользователя они выключены, поэтому окно опирается только на `ICCameraDeviceCanDeleteOneFile`.

Если выделенные снимки сейчас копируются, удаление ждёт конца копирования. Если копирование не удалось, окно спрашивает, удалять ли.

### D7. Общий код с окном Android

Из `FileBrowserTable.swift` выносятся без изменения поведения: `LatinKey`, обёртка `PromiseDelegate`, `FileTransfer`/`TransferRow`. Окно Android после выноса проверяется сборкой и коротким ручным прогоном (⌘C, перетаскивание).

## Risks / Trade-offs

- [iPhone с «Фото iCloud» и «Оптимизацией хранилища» отдаёт только то, что лежит на устройстве, и, возможно, не даёт удалять] → окно говорит об этом. Проверка на iPhone пользователя — задача 1.1, до основной работы.
- [Пока окно открыто, PTP-сессия занята: «Фото» и «Захват изображений» могут не видеть iPhone] → сессия только пока окно открыто.
- [Тысячи снимков: долгое чтение каталога] → показываем прочитанное по мере прихода, миниатюры лениво. На 192 файлах каталог пришёл за 0,1 с.
- [Новые снимки видны только после переподключения кабеля] → подсказка под списком.
- [Удаление необратимо, если iPhone не кладёт в «Недавно удалённые»] → подтверждение с числом снимков. В README сказано, проверять ли «Недавно удалённые».
- [Только кабель] → сказано в окне и README.

## Open Questions

- Окно разрешения macOS для самого приложения (из терминала его не было) — проверяется в 4.3.
- Удаление при включённых «Фото iCloud» — не на чем проверить.
