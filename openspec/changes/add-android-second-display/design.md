# Design

## Context

См. proposal.md — зачем. Что уже есть: `adb` (USB и Wi‑Fi, общий `ADBClient`/`ADBSocket`), установка собственного APK и проверка его версии (`MotionCameras`, `scripts/build-motion-apk.sh`, ключ подписи в `~/.config/universalkm/`), `forward` на abstract-сокет приложения (как у помощника буфера обмена), право «Универсальный доступ» для событий ввода. Чего нет: права «Запись экрана», любого видеокодирования на Mac, виртуальных дисплеев.

## Goals / Non-Goals

**Goals:** задержка до 80 мс по USB; одна кнопка; дисплей как настоящий второй монитор macOS; ничего не остаётся на Mac и устройстве после отключения.

**Non-Goals:** звук, зеркальный режим, перо, несколько мониторов сразу, своё сжатие лучше H.264, драйверы ядра/DriverKit.

## Decisions

### D1. Виртуальный дисплей — `CGVirtualDisplay`, а не драйвер
Приватные классы `CGVirtualDisplayDescriptor`, `CGVirtualDisplaySettings`, `CGVirtualDisplayMode`, `CGVirtualDisplay` из CoreGraphics (их используют DeskPad и BetterDisplay): работают из обычного приложения без прав администратора и без расширения ядра. Объявления — в маленькой ObjC-цели `UniversalKMDisplay` с заголовком-интерфейсом; Swift вызывает её как обычный код. Режим — пиксели устройства (не больше 2560 по длинной стороне), масштаб 1× (точки = пиксели), частота 60 Гц; дисплей получает имя «UniversalKM · <имя устройства>» и серийный номер от устройства, чтобы macOS помнила его расположение между включениями.
*Альтернативы:* DriverKit-расширение (требует подписи и разрешения Apple, ставится пользователем вручную, на порядок тяжелее); HDMI-«заглушка» (железо); зеркалить основной монитор (не расширяет рабочий стол — не Sidecar).

### D2. Захват — ScreenCaptureKit по `displayID`
`SCStream` с фильтром на созданный дисплей, `showsCursor = true`, 60 кадров/с, `queueDepth = 3`, формат `420YpCbCr8BiPlanarVideoRange` — сразу в кодер, без копий. Для захвата нужно право «Запись экрана»; без него `SCShareableContent` отдаёт ошибку, это причина для сообщения пользователю (spec «Права и ошибки»). Кадры приходят только при изменении изображения; кодер получает ещё и повтор последнего кадра раз в секунду, чтобы декодер на устройстве не считал поток оборванным.
*Альтернатива:* `CGDisplayStream` (устарел, тоже требует права).

### D3. Кодирование — VideoToolbox H.264, режим малой задержки
`VTCompressionSession`: профиль High (если нет — Main), `RealTime = true`, без B-кадров (`AllowFrameReordering = false`), `MaxKeyFrameInterval` 120 кадров и ключевой кадр по запросу устройства, `ExpectedFrameRate = 60`, битрейт 12 Мбит/с по USB и 6 Мбит/с по Wi‑Fi (`DataRateLimits` — окно 1 с). SPS/PPS отправляются перед каждым ключевым кадром. H.264, а не HEVC: аппаратный декодер H.264 есть на каждом Android, HEVC на части старых устройств и в низкой задержке хуже.

### D4. Транспорт — один сокет, поток вперёд и события назад
Приёмник слушает abstract-сокет `localabstract:ukm_display` (`LocalServerSocket`); Mac делает `adb forward tcp:0 localabstract:ukm_display` и подключается — тот же приём, что у помощника буфера обмена и scrcpy (add-android-screen-mirror D2). Версию протокола стороны сверяют в первом сообщении, при несовпадении Mac предлагает обновить приёмник. Сообщения — `u8 тип`, `u32 длина`, тело:
- Mac → устройство: `CONFIG` (SPS/PPS, ширина, высота), `FRAME` (флаги, PTS в мкс, данные Annex B);
- устройство → Mac: `HELLO` (версия, размер экрана в пикселях, ориентация, поддержка кодека), `KEYFRAME_REQUEST`, `ROTATED` (новый размер), `TOUCH` (на этапе 2), `STATS` (время декодирования и показа, раз в секунду).
TCP_NODELAY на обеих сторонах; по Wi‑Fi — тот же сокет через `adb`. Разбор и сборка сообщений — в `UniversalKMCore` с тестами при любом разрезе потока.
*Альтернатива:* свой USB-канал через AOA — быстрее на несколько миллисекунд, но второй стек, и Wi‑Fi не покрывает.

### D5. Приёмник — отдельный APK
`com.universalkm.display`: одно `Activity` (`SurfaceView`, `immersive sticky`, `FLAG_KEEP_SCREEN_ON`, `screenOrientation=fullSensor`), `MediaCodec` H.264 с `KEY_LOW_LATENCY` (API 30+) и `KEY_PRIORITY = 0`, вход — прямо из сокета, вывод — на `Surface` без копий. Разрешений не просит: `LocalServerSocket` не использует сеть, `INTERNET` не нужен. Сборка — `scripts/build-display-apk.sh` по образцу `build-motion-apk.sh`, свой `version.properties`; запуск — `adb shell am start -n …` после `forward`; обновление — по versionCode, как у камеры. Отдельный APK, а не часть камеры движения: у камеры камера/микрофон/фон, у монитора ничего из этого нет, и пользователь, ставящий только монитор, не получает лишних прав.
*Альтернатива:* приёмник в браузере телефона (WebRTC/MSE) — не нужен APK, но задержка 150+ мс и нет полноэкранного режима без жестов браузера.

### D6. Касания (этап 2)
Касание в приёмнике → нормализованные координаты (0…1 по картинке) → `TOUCH` с типом (вниз/движение/вверх, число пальцев). Mac переводит в точку виртуального дисплея (его рамка из `CGDisplayBounds`) и шлёт `CGEvent` мыши (`.leftMouseDown/Dragged/Up`, `.scrollWheel` для двух пальцев, `.rightMouseDown/Up` для долгого касания 0.5 с). Не двигать `CGWarpMouseCursorPosition` чужих мониторов: курсор появляется на виртуальном дисплее только пока палец касается; после отпускания возвращается на прежнее место. Нужно право «Универсальный доступ» — оно приложению уже нужно. Это не `InputManager` (тот перехватывает события клавиатуры/мыши с Mac для передачи на устройства); новый код только создаёт события.

### D7. Жизненный цикл и поворот
Порядок: проверка права «Запись экрана» → установка/обновление APK → `am start` → `forward` → подключение, `HELLO` → создание дисплея по размеру из `HELLO` → захват и кодирование → `CONFIG`. Отключение — в обратном порядке; дисплей удаляется освобождением объекта `CGVirtualDisplay`. Поворот: `ROTATED` → смена режима дисплея через `applySettings` (дисплей остаётся, окна остаются, нужен ключевой кадр и новый `CONFIG`). Обрыв сокета — удалить дисплей в течение 5 с (`adb` уже имеет опрос состояния устройств); на устройстве приёмник при обрыве показывает «Ожидание Mac…» и через 60 с закрывается.

### D8. Режим устройства — переключатель
Устройство в панели работает либо как «Клавиатура и мышь» (край-зона, HID), либо как «Монитор»: переключатель (segmented) в карточке устройства над выключателями. Выбор «Монитор» запускает сеанс и выключает зону передачи ввода этого устройства (`AppStateManager.monitorPeers`; как `inputEnabled = false`, но без изменения сохранённой настройки: после «Клавиатура и мышь» всё как было). Для Android с выключенным вводом транспорт снимает HID-привязку, поэтому экранная клавиатура на планшете работает при касаниях. Режим не сохраняется между запусками: после перезапуска устройство снова в режиме «Клавиатура и мышь». Один монитор одновременно. Прежний значок монитора в строке «Камера движения» убран.

### D9. Положение и ориентация — из раскладки, размер — 1:1 с пикселями устройства
Прямоугольник устройства в раскладке (`DeviceLayout.rect`, глобальные точки CG, как у мониторов) определяет **место и ориентацию** дисплея: после создания `CGConfigureDisplayOrigin` ставит дисплей в `rect.origin` (край, сдвиг), повторяя при смене раскладки. Размер дисплея — пиксели устройства (не больше 2560 по длинной стороне), точки равны пикселям. Физический размер из раскладки на размер не влияет.
*Проверено 2026‑11‑21 (macOS 27):* режим HiDPI у `CGVirtualDisplay` удваивает размер (запрошено 594×996 → 1188×1992 точек, пикселей столько же, без Retina), поэтому «логический размер из физического» невозможен без своего масштабирования; первый прототип 1:1 владельца устроил. Виртуальный дисплей исключается из списка мониторов раскладки (по `CGDisplayVendorNumber`), иначе устройство могло бы встать рядом с самим собой. Размер экрана в пикселях из HELLO записывается в `screenPixels` устройства, если там пусто или пропорции не совпадают (>1%): без этого прямоугольник раскладки не знает настоящих пропорций.
*Альтернативы:* свой масштаб при захвате (картинка размером с физический размер, пикселей меньше) — мельче картинка, отложено.

### D10. Ориентация следует за устройством
`ROTATED` → `setOrientation(…, source: .device)` меняет прямоугольник в раскладке, затем дисплей получает новый режим и положение; обратное тоже верно: поворот кнопкой в раскладке при включённом мониторе не меняет устройство (его поворачивает пользователь), поэтому кнопка поворота в раскладке при включённом мониторе скрыта.

## Risks / Trade-offs

- [Apple меняет или закрывает `CGVirtualDisplay`] → цель с приватным API изолирована, при сбое создания дисплея кнопка показывает причину; запасной путь — DriverKit, отдельным изменением.
- [Задержка больше 80 мс] → этап 1 заканчивается замером; если по USB выше 120 мс, изменение останавливается и пересматривается (меньше буферов, `max_size`, HEVC, свой USB-канал).
- [Права «Запись экрана» — новое разрешение] → запрашивается только при первом включении, с объяснением; перезапуск приложения после выдачи, если macOS его потребует.
- [Play Protect долго проверяет APK] → как у камеры: «Установка идёт дольше обычного» после 15 с.
- [Окна «прыгают» при включении/отключении монитора] → так делает macOS с любым монитором; положение запоминается по серийному номеру (D1).
- [Нагрев и батарея устройства] → при включённом мониторе экран всегда горит; в приёмнике показывается заряд, а Mac при 15% предупреждает.

## Migration Plan

Новая функция, миграции нет. Откат — убрать кнопку и цель `UniversalKMDisplay`; `ukm-display.apk` с устройства удаляется обычным способом.

## Open Questions

- Масштаб: по умолчанию 1× (точки = пиксели) — на телефоне 1080×2280 текст мелкий. Предложить «Крупнее» (масштаб 1.5× и 2× через HiDPI-режим) после замера; решать по результатам этапа 1, на спецификацию это не влияет.
