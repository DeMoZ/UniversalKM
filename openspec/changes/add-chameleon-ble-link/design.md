# Design

## Context

Зачем — proposal.md, раздел «Why». Требования — `specs/chameleon-wireless-link/spec.md`. Изменение строится поверх `add-ble-hid-input-bridge` (дальше — «базовое изменение», ссылки вида «базовый D5»).

Что есть сейчас (проверено в коде и в апстриме на зафиксированном коммите `4c5bc2c`):

- **Каналы Mac → Chameleon: USB‑CDC и Bluetooth через NUS** (базовый D5, задача 1.15, релиз 0.1.0): кадры `netdata`, команды 9000–9006, один кадр в полёте. По Bluetooth приложение (`ChameleonBLELink`) подключается как central, подписывается на NUS TX; прошивка считает это соединение каналом управления (`ukm_hid_on_nus_comm`): оно не HID‑хост, ответы NUS идут ему с его MTU. Свой Chameleon приложение находит по адресу устройства в scan response режима HID (manufacturer data `FF FF` + адрес из команды 1012). `ChameleonHIDTransport` работает по USB, держит Bluetooth‑канал в запасе и переходит на него, когда USB пропадает, без выключения режима HID.
- **Прошивка отвечает по USB, пока порт открыт** (`auto_response_data` апстрима), поэтому по Bluetooth нельзя ничего спросить, пока Chameleon на кабеле.
- **Проверено (2026‑11‑08): macOS сама сопрягается с Chameleon,** когда приложение подключается через CoreBluetooth: соединение Mac через ~1 с подписано на HID‑отчёты и получает peer ID (bond), Chameleon появляется в настройках Bluetooth как клавиатура; если Mac сопряжён как HID‑хост, нажатия до него доходят («hello» напечаталось в чате). После выхода приложения система держит это соединение (базовая прошивка теперь рвёт все соединения при выключении режима HID). Это результат спайка 1.1: подход D3 «Mac не подписывается на HID» сам по себе не работает — сопряжение инициирует система, а не приложение.
- **NUS открыт в режиме HID без PIN.** `ble_nus.c` ставит `SEC_OPEN`, если PIN выключен (`SEC_MITM` — если включён), а режим HID работает именно без PIN. Команды 9001–9003 через NUS выполняются — это дыра, которую закрывает это изменение.
- **В апстриме уже собраны `nrf_crypto` и бэкенд CC310** (аппаратный CryptoCell nRF52840): в `sdk_config.h` включены `CHACHA_POLY`, `AES_CCM`, HKDF‑исходники в Makefile. Свою криптографию писать не нужно.
- **Ограничения SoftDevice в `sdk_config.h`:** `NRF_SDH_BLE_PERIPHERAL_LINK_COUNT 3` (после базового изменения), `NRF_SDH_BLE_GAP_EVENT_LENGTH 3` (3,75 мс), `NRF_SDH_BLE_GATT_MAX_MTU_SIZE 247`, `NRF_SDH_BLE_VS_UUID_COUNT 1` (занят NUS), таблица атрибутов 2048 байт.
- **Сон апстрима:** таймер сна останавливается при BLE‑подключении и при питании от USB; после отключения BLE — 4 с, после пропадания USB‑питания — 3 с, после пробуждения кнопкой — 8 с (`syssleep.h`). Режим HID выключен после каждого сброса (базовый D3).
- **macOS:** роль BLE central через CoreBluetooth доступна любому приложению (нужно разрешение Bluetooth и `NSBluetoothAlwaysUsageDescription`). Интервал соединения выбирает macOS; периферия может только попросить. По рекомендациям Apple для аксессуаров минимальный интервал — 15 мс.

## Goals / Non-Goals

**Goals:**
- Mac управляет Chameleon по Bluetooth так же, как по USB, с теми же гарантиями доставки (без потерь клавиатуры, со слиянием мыши — базовый D5).
- Канал защищён от посторонних в радиусе Bluetooth: нельзя ни вводить текст на телефон, ни прочитать набранное.
- Приложение само выбирает USB или Bluetooth; модули перехвата ввода и панели работают с тем же протоколом `HIDTransport`.

**Non-Goals:**
- Перепрошивка Chameleon по Bluetooth (DFU по воздуху). Прошивка и первое сопряжение — только кабелем.
- Работа с несколькими Mac одновременно; один Chameleon — один сопряжённый Mac.
- Управление Chameleon с iPhone/Android по этому каналу.
- Использование NUS для команд режима HID (NUS остаётся только для штатного клиента Chameleon).

## Decisions

### D1. Mac — BLE central, Chameleon — периферия с дополнительным соединением

Mac подключается к Chameleon как central (CoreBluetooth `CBCentralManager`) — так уже работает NUS‑канал базовой 1.15. Chameleon остаётся периферией для всех: до трёх HID‑хостов плюс одно соединение Mac, итого `NRF_SDH_BLE_PERIPHERAL_LINK_COUNT` 3 → 4 (сейчас Mac занимает одно из трёх).

**Как не дать macOS сопрячься (открыто, решить в спайке 1.2):** система сопрягается сама, потому что видит HID‑сервис и характеристики с шифрованием. Варианты: (а) прошивка отвечает отказом на запрос сопряжения (`BLE_GAP_SEC_STATUS_PAIRING_NOT_SUPP`) соединению, которое подписалось на сервис UniversalKM или NUS, и удаляет его bond, если он уже есть; macOS должна сдаться, а сеанс UniversalKM шифрования BLE не требует (D3); (б) то же, но решение по адресу Mac, записанному при сопряжении по кабелю (адрес в CoreBluetooth не виден, но прошивка видит адрес соединения, открывшего сеанс). Проверка: Chameleon не появляется в настройках Bluetooth Mac, нажатия на Mac не приходят.

*Альтернатива:* Mac как периферия со своим сервисом (`CBPeripheralManager` такие сервисы разрешает), Chameleon — как central к нему. Отвергнута: Chameleon пришлось бы включить роль central в SoftDevice (ещё RAM и код сканирования), а реклама Mac работает только пока приложение её держит — выигрыша нет.

### D2. Свой GATT‑сервис UniversalKM, а не NUS

Новый сервис с 128‑битным UUID (база UUID — вторая, `NRF_SDH_BLE_VS_UUID_COUNT` 1 → 2), модуль `firmware/src/ukm_link.c`:

- **RX** — Write Without Response, до 244 байт (MTU 247): пакеты от Mac.
- **TX** — Notify: пакеты Chameleon → Mac.
- Безопасность характеристик — `SEC_OPEN`: защита на уровне приложения (D3).

Почему не NUS, хотя он уже передаёт `netdata`:
1. `dataframe.c` держит один кадр, и цикл «запрос → ответ» по BLE стоит два интервала соединения (~30 мс) — мышь работала бы с частотой ~30 Гц. Свой сервис принимает пакеты прямо в обработчике BLE, без однокадрового буфера.
2. Ответы NUS адресованы `m_conn_handle` — последнему соединению, а не отправителю.
3. NUS нужен штатному клиенту Chameleon, его безопасность зависит от PIN апстрима.

Из NUS в режиме HID команды 9001–9003 отвергаются (патч `app_cmd.c`: если команда пришла не из USB и режим HID включён — статус `0x60`/«не разрешено»). Для этого `data_frame_receive` получает признак источника (USB или NUS).

### D3. Ключ сопряжения + сеанс с AEAD вместо системного Bluetooth‑сопряжения

**Выбор:** Mac и Chameleon делят секретный ключ `K` (32 байта), переданный один раз по USB. Каждый беспроводной сеанс выводит из него новые ключи и шифрует пакеты ChaCha20‑Poly1305.

*Почему не системное сопряжение (LESC bonding) Mac ↔ Chameleon:*
- В таблице GATT Chameleon всегда есть HID‑сервис (базовый D3, менять таблицу на ходу нельзя). Сопряжённый Mac может подключить Chameleon как свою клавиатуру/мышь (системный HID‑драйвер подписывается на отчёты) — противоречит spec «Без системного сопряжения Mac».
- У Chameleon нет экрана и клавиатуры: без PIN остаётся Just Works, который не защищает от MITM при сопряжении; с PIN апстрима ломается сопряжение телефонов (они тоже спросят PIN).
- CoreBluetooth не даёт управлять сопряжением (OOB, выбор метода).

Сопряжение по кабелю даёт настоящий общий секрет без MITM: кабель физически у пользователя.

**Сеанс** (все примитивы стандартные: CryptoKit на Mac, `nrf_crypto` CC310 в прошивке):
1. Mac → `HELLO`: `[0x01, nonceM 16 байт]` открытым текстом.
2. Chameleon → `CHALLENGE`: `[0x02, nonceC 16 байт]` (`nonceC` — из аппаратного ГСЧ, `sd_rand_application_vector_get`).
3. Обе стороны: `HKDF‑SHA256(ikm = K, salt = nonceM ‖ nonceC, info = "UniversalKM link v1", 64 байта)` → `kM2C ‖ kC2M`. Ключи разные для направлений, поэтому одинаковые одноразовые числа (nonce) в двух направлениях не повторяют пару «ключ + nonce».
4. Каждый следующий пакет: `[type u8, counter u32 LE, ciphertext, tag 16]`, nonce AEAD = `counter LE ‖ 8 нулевых байт`, AAD = `[type, counter]`. Первый пакет Mac (`counter 0`, `PING`) доказывает знание `K`; первый пакет Chameleon (`STATE`, `counter 0`) — тоже. До проверки первого пакета Mac Chameleon не выполняет команд; нет проверки за 5 с — разрыв соединения.
5. Счётчик строго растёт; пакет с неверным тегом или счётчиком ≤ последнего принятого отбрасывается. Переполнение `u32` невозможно за разумное время (сеанс переоткрывается при каждом подключении).

Накладные расходы: 21 байт на пакет; отчёт мыши — 31 байт, укладывается в один пакет при MTU ≥ 34 (macOS договаривается о 185+).

`linkId` (4 случайных байта, выдаёт Chameleon при сопряжении) — публичный идентификатор для поиска (D7), не секрет.

### D4. Содержимое пакетов и доставка

Расшифрованное содержимое — `[cmd u8, данные]`, данные — как у USB‑команд базового D5:

| cmd | Направление | Данные |
|---|---|---|
| 0x10 `SET_ENABLED` | Mac → C | `[0/1]` |
| 0x11 `KEYBOARD` | Mac → C | `[seq u16, peerId u16 BE, 8 байт отчёта]` |
| 0x12 `MOUSE` | Mac → C | `[peerId u16 BE, 7 байт отчёта]` |
| 0x13 `NEUTRAL` | Mac → C | — (нейтральные отчёты всем хостам) |
| 0x14 `PING` | Mac → C | — (раз в 500 мс в простое) |
| 0x20 `STATE` | C → Mac | как ответ 9004 + `[battery %, kbAckSeq u16]` |
| 0x21 `KB_RESEND` | C → Mac | `[seq u16]` — очередь переполнена, повторить с этого номера |

- **Клавиатура без потерь.** Write Without Response подтверждается на канальном уровне BLE, поэтому пакет, отправленный в живое соединение, доходит. В прошивке отчёты клавиатуры кладутся в FIFO на 32 элемента в `ukm_hid` и уходят хосту по мере освобождения очереди HVN (`BLE_GATTS_EVT_HVN_TX_COMPLETE`). Переполнение → `KB_RESEND`; Mac хранит неподтверждённые отчёты (подтверждение — `kbAckSeq` в `STATE`) и повторяет. Отчёт с уже принятым `seq` прошивка пропускает — повторов на телефоне нет.
- **Мышь со слиянием на обеих сторонах.** Mac шлёт отчёт, только когда `peripheralIsReady(toSendWriteWithoutResponse:)`/`canSendWriteWithoutResponse`; до этого движение копится в `MouseAccumulator` (базовый D5). Прошивка, получив отчёт мыши при занятой очереди HVN, складывает его с уже ожидающим (X/Y/колесо суммируются, кнопки берутся новые; смена кнопок отправляет накопленное отдельным отчётом — как в базовом D5).
- **Состояние без опроса.** `STATE` Chameleon шлёт сам: при каждом изменении хостов и раз в 1 с. По USB опрос 250 мс остаётся как есть (базовый D6).
- **Где выполняется работа.** Обработчик BLE (контекст прерывания SoftDevice) только копирует пакет в кольцевой буфер на 8 пакетов; расшифровка CC310 и вызов `ukm_hid` — в главном цикле апстрима (как обработка `dataframe`). Это добавляет < 1 мс, но не вызывает CC310 из прерывания.
- **Потеря сеанса.** Разрыв соединения Mac или 1,5 с без валидного пакета → `ukm_hid` шлёт нейтральные отчёты всем хостам (та же функция, что `ukm_hid_on_usb_lost`).

### D5. Слоты соединений

Четыре соединения, но при подключении неизвестно, кто это — телефон или Mac. Правило в `ukm_hid`/`ukm_link`: соединение, открывшее сеанс UniversalKM, — Mac‑соединение (не HID‑хост, не попадает в 9004/`STATE`, не привязывается к устройствам на схеме). Остальные — кандидаты в хосты. Если кандидатов становится больше трёх, самый новый, не открывший сеанс за 5 с, разрывается. Реклама продолжается, пока соединений меньше четырёх и (нет Mac‑соединения или хостов меньше трёх).

Следствия для SoftDevice: ещё одно соединение → больше RAM (патч `0006`, ещё +~4 КБ с запасом; ошибка видна сразу на старте, как в базовом D3), вторая база UUID, атрибуты нового сервиса (~6 записей) укладываются в 2048 байт таблицы — проверить по `sd_ble_gatts_*` при старте.

### D6. Интервал соединения с Mac и задержка

Для Mac‑соединения прошивка просит 15–30 мс (`ble_conn_params_change_conn_params` по `conn_handle` этого соединения), slave latency 0. macOS обычно даёт 15 мс. Путь отчёта: Mac → Chameleon до одного интервала (≤ 15 мс) + обработка < 1 мс + Chameleon → хост до одного интервала хоста (7,5–15 мс) ≈ 23–31 мс в худшем случае без коллизий. Отсюда требование 95‑го перцентиля ≤ 40 мс. Соединения разных central не синхронизированы, и радиособытия иногда пересекаются; SoftDevice переносит пересёкшееся событие на следующий интервал — это хвост распределения, его покрывает запас до 40 мс.

Замер: диагностическая команда `PING` с меткой времени Mac, Chameleon возвращает её в следующем `STATE` вместе со временем отправки хосту (`BLE_GATTS_EVT_HVN_TX_COMPLETE`); половина RTT + время до HVN — оценка задержки.

### D7. Поиск Chameleon по Bluetooth

CoreBluetooth не показывает BLE‑адрес, поэтому:
- В scan response Chameleon, если ключ сопряжения есть, добавляются Manufacturer Specific Data: `[0x59, 0x00 (Nordic), 'U','K', linkId 4 байта]` — 10 байт рядом с именем `ChameleonUltra` (16 байт), всего 26 ≤ 31. Заменяют нынешние `[FF FF, адрес 6 байт]` базовой 1.15 (адрес открыт любому, `linkId` появляется только после сопряжения по кабелю). Это делается и в режиме HID (`ble_advertising_hid_mode_set`), и в штатной рекламе апстрима, иначе после пробуждения (режим HID выключен) Mac Chameleon не найдёт.
- Mac сканирует с активным сканированием и ищет свой `linkId`; найденный `CBPeripheral.identifier` запоминает и дальше подключается по нему (`retrievePeripherals(withIdentifiers:)` + `connect`: ожидающее подключение macOS держит сам, пока Chameleon не появится).
- После подключения: `discoverServices([UKM])`, подписка на TX, `HELLO`. На HID‑сервис Mac не подписывается и шифрование не запрашивает (D3).

### D8. USB‑команды сопряжения и версия протокола

| ID | Команда | Запрос | Ответ |
|---|---|---|---|
| 9010 | `UKM_LINK_PAIR` | `[K 32 байта]` | `[linkId u32]`; ключ и `linkId` записываются в FDS |
| 9011 | `UKM_LINK_FORGET` | — | — ; запись FDS стирается, открытый сеанс закрывается |
| 9012 | `UKM_LINK_INFO` | — | `[paired u8, linkId u32, macConnected u8, sessionActive u8]` |
| 9013 | `UKM_LINK_SELFTEST` | — | результат шифрования тестового вектора (D10) |

Команды 9010–9013 принимаются только по USB. `UKM_HID_GET_INFO` (9000) отдаёт `protocolVersion = 3`; приложение предлагает беспроводной режим только при версии ≥ 3, иначе в панели «Обновите прошивку Chameleon, чтобы работать без кабеля».

Ключ во флеше — запись FDS со своими file id/record key (новые константы рядом с `fds_ids.h` апстрима; запись через `fds_write_sync`, как `settings.c`). Утечка ключа требует физического доступа к Chameleon (SWD/DFU); «Забыть Chameleon» и повторное сопряжение меняют его.

На Mac ключ — `kSecClassGenericPassword`, сервис `UniversalKM.ChameleonLink`, учётная запись = `linkId`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (не уходит в iCloud). В логах и UI ключ не показывается.

### D9. Транспорт в приложении

- Bluetooth‑канал уже есть: `ChameleonBLELink` (CoreBluetooth на очереди транспорта `ukm.serial`) под `ChameleonHIDTransport`, который выбирает канал. Меняется содержимое канала: вместо кадров `netdata` в NUS — пакеты сеанса UniversalKM (`LinkSession`/`LinkPacket`); USB остаётся на кадрах `netdata`.
- Кодек и криптография — в Core, без CoreBluetooth: `LinkSession` (HKDF + ChaChaPoly из CryptoKit, счётчики, проверка повторов), `LinkPacket` (кодирование/разбор), `KeyboardOutbox` (неподтверждённые отчёты по `seq`). Всё покрывается unit‑тестами.
- Выбор канала остаётся как в базовой 1.15: USB подключён → активен USB, Bluetooth‑сеанс открыт и ждёт в запасе (пользователь хочет, чтобы выдёргивание кабеля не прерывало работу; цена — слот соединения и батарея); USB пропал → работа идёт по Bluetooth без возврата ввода на Mac. Привязки `PlacedDevice.hostPeerID` не трогаются — `peerId` Peer Manager одинаков в обоих каналах.
- Разрешение Bluetooth запрашивается только когда пользователь нажал «Сопрячь…» или ключ уже сохранён — чтобы пользователи с кабелем не видели лишнего запроса.

### D10. Общие тестовые векторы

`firmware/test-vectors/link-v1.json`: `K`, `nonceM`, `nonceC`, ожидаемые `kM2C`/`kC2M`, пакеты с известными counter/plaintext и их шифртекст+тег. Swift‑тесты проверяют по нему `LinkSession`. Прошивка проверяется командой 9013: она шифрует тот же вектор на CC310 и возвращает результат; скрипт `scripts/link-selftest.sh` сравнивает его с JSON по USB. Так обе реализации проверены против одного эталона, а не друг против друга.

### D11. Сон и батарея

Патчи сна апстрима (только когда есть ключ сопряжения, иначе поведение апстрима не меняется):
- Есть сеанс Mac или USB‑питание → таймер сна остановлен.
- Пропало USB‑питание и сеанса Mac нет → режим HID выключается сразу (базовое «Выключение режима HID без связи с Mac», решение пользователя: телефоны должны сразу вернуть экранную клавиатуру), дальше сон апстрима через 3–4 с. Десятиминутного ожидания нет.
- Пробуждение кнопкой даёт апстримные 8 с; подключение Mac за это время останавливает таймер (ожидающее подключение CoreBluetooth срабатывает за ~1 с после начала рекламы).

Заряд — значение, которое апстрим уже измеряет для Battery Service, передаётся в `STATE`. Порог предупреждения — 15 %.

## Risks / Trade-offs

- [macOS даёт Mac‑соединению интервал 30 мс, а не 15] → задержка выше 40 мс. Митигация: спайк в группе 1 измеряет интервал до основной работы; если 15 мс не получить, требование задержки пересматривается с пользователем до реализации групп 3–5.
- [macOS всё же подключает HID Chameleon, увидев сервис 0x1812, даже без сопряжения] → Chameleon стал бы клавиатурой Mac. Митигация: тот же спайк проверяет; HID‑характеристики требуют шифрования, а Mac его не запрашивает, поэтому подписка на отчёты невозможна без сопряжения.
- [Коллизии радиособытий четырёх несинхронизированных соединений] → дрожание задержки и пропущенные интервалы. Митигация: слияние мыши на обеих сторонах, очередь клавиатуры; замер в задаче 5.2.
- [Ошибка в протоколе сеанса] → Митигация: только стандартные AEAD и HKDF, раздельные ключи направлений, новый ключ на каждый сеанс, общие тестовые векторы (D10), тесты на повтор и подмену.
- [Батарея Chameleon маленькая] → работа без кабеля может длиться часы, а не дни. Митигация: без Mac и USB режим HID выключается сразу и Chameleon засыпает, предупреждение о заряде, USB остаётся основным вариантом; реальное время измеряется и пишется в README.
- [RAM SoftDevice для 4‑го соединения] → ошибка `nrf_sdh_ble_enable` на старте. Митигация: как в базовом D3 — видно сразу после прошивки, откат кнопкой B в DFU.
- [Посторонний занимает 4‑й слот соединения] → Mac не может подключиться. Митигация: правило 5 с из D5; соединение без сеанса и без HID‑подписки разрывается.
- [Сопряжение по кабелю неудобно] → Делается один раз и совпадает с первой прошивкой, которая и так требует кабеля.

## Migration Plan

1. Прошивка с протоколом 3 ставится тем же DFU по кабелю (`scripts/firmware-flash.sh`); без ключа сопряжения она ведёт себя как прошивка протокола 2, кроме отказа команд HID через NUS.
2. Приложение со старой прошивкой работает только по USB и предлагает обновить прошивку.
3. Откат: официальная прошивка через DFU (базовый D16) стирает и режим HID, и ключ; ключ в связке ключей Mac удаляется кнопкой «Забыть Chameleon».
